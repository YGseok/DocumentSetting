# 디폴트: 공통 문서 작성 규칙

이 규칙은 게임·프로젝트와 무관하게 모든 문서 작성 작업의 기본 기준으로 적용한다. 구체적인 형식은 문서의 목적과 사용자 요청에 맞춘다.

## 1. 목적과 범위

- 문서의 목적, 독자에게 전달할 핵심, 적용 범위를 먼저 드러낸다.
- 개선·변경 문서는 필요에 따라 현황 → 문제 → 제안 → 적용 범위를 설명한다.
- 기능이나 규칙을 제안할 때는 사용자가 얻는 결과나 판단에 도움이 되는 이유를 연결한다.
- 기존 내용, 신규 추가, 변경 내용, 적용 예외를 명확히 구분한다.

## 2. 구성과 문장

- 개발·업무 기획서는 짧고 명확한 개조식 항목을 기본으로 한다. 설명문 등 연속된 논지가 중요한 문서는 문단으로 작성한다.
- 상위 항목에 핵심 주장·규칙·동작을, 하위 항목에 조건·이유·예외·세부 정보를 배치한다.
- 구조가 긴 문서는 번호가 있는 제목과 하위 제목으로 구분한다. 짧은 문서에 불필요한 장을 만들지 않는다.
- 고정 목차를 모든 문서에 강제하지 않는다. 자료가 없는 장을 채우기 위해 내용을 만들어내지 않는다.
- 명확한 동작과 상태를 표현하고, 같은 뜻의 장황한 반복을 줄인다.

## 3. 규칙과 처리 설명

- 처리 시점 → 조건 → 동작 → 결과의 관계가 읽히게 작성한다.
- 상태별 분기가 실제로 필요한 경우 구분한다. 적용되는 범위와 예외를 함께 설명한다.
- 정렬 기준, 갱신 시점, 횟수, 경계값, 완료 조건은 해당 내용의 이해·구현에 필요할 때 명시한다.
- 기존 규칙을 재사용할 경우 재사용 범위를 밝히고, 별도 상세 문서가 있으면 연결한다.
- 수치·일정·정책·식별자를 근거 없이 확정하지 않는다. 모호한 사항은 미정으로 표시하거나 작업을 좌우하는 정보만 질문한다.

## 4. 표와 시각 자료

- 비교, 상태 정의, 데이터 구조, 이름과 값의 대응은 표로 정리한다.
- 화면과 흐름을 설명할 때 이미지·도식·번호 주석을 활용한다. 번호와 본문 설명이 서로 대응해야 한다.
- UI 문서는 화면 간 이동과 화면 내부 요소를 구분한다. 필요한 표시 정보·상태·조작 결과를 적는다.
- 강조는 핵심 정의, 중요한 차이, 예외에 한정한다. 색상만으로 의미를 전달하지 않는다.
- 이미지가 제공되지 않았거나 직접 확인하지 못했다면 관찰한 것처럼 설명하지 않는다.

## 5. 데이터와 제작 요청

- 표, 컬럼, 키, 코드, 경로, 가변 인자의 원문 철자를 보존한다.
- 새 식별자나 값은 제안 상태임을 표시한다.
- 데이터 정의는 이름·타입·의미·참조 관계 등 실제로 필요한 정보를 포함한다.
- 제작 요청은 대상·용도·경로와 신규 제작/재사용/수정 여부가 전달되게 작성한다.
- 관련 문서 링크는 필요한 설명 가까이에 둔다. 프로젝트별 실제 경로는 레퍼런스 영역에서 관리한다.

## 6. 미결정 사항과 출처

- 확인된 사실, 사용자의 요구, 작성자의 제안, 미결정 사항을 구분한다.
- 복수안은 선택되지 않은 상태를 유지한다. “논의 필요”, “확인 필요”, “추가 예정”을 임의로 확정하지 않는다.
- 여러 작업자의 자료가 섞여 있을 때는 사용자가 지정한 문서만 개인 작성 스타일의 근거로 삼는다.
- 문서에 적힌 설계가 실제 반영 상태를 증명하지는 않는다. 출처 간 차이가 있으면 시점과 적용 범위를 확인한다.
- 원문의 중복 번호, 오타, 불명확한 표현은 그대로 모방하지 않는다.

## 7. 전달과 유지

- 출력 형식은 사용자 요청을 따른다. 노션용 요청은 제목·목록·표 중심의 옮기기 쉬운 Markdown을 기본으로 한다.
- 로컬 파일 저장과 외부 서비스 반영 여부를 구분해 보고한다.
- 공통 규칙 변경은 이 파일에, 프로젝트 지식과 사례는 해당 레퍼런스에 기록한다.
- 현재 지시와 충돌하는 과거 규칙은 갱신하여 중복과 모순을 줄인다.
